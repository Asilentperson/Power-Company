## 1. 五条设计哲学 → 落点

| 哲学 | 代码/契约落点 | 一句话检验 |
|---|---|---|
| 实体经营与股市两张皮合一 | `dispatch` → `company.IncomeStatement` → `valuation` → `ma` | 任何新系统都必须把结果写进利润表，否则就是副玩法 |

| 重资产压力感 | `Company.fixed_cost_q` / `Plant.fixed_q` / 工资刚性 | 不发电也扣钱；研发不成功也扣钱 |
| 2D 表达 | `ui/mapview.py` 单格绘制 + 右栏页签 | 不进 3D、不做进度条 |

## 2. 一回合六阶段 ↔ `Game.end_turn` 流水线

玩家的六阶段与代码的执行顺序**不是**一一对应：阶段 2、3 是 `end_turn()` **之前**的 UI 操作，阶段 4~6 才是 `end_turn()` 内部。

| 设计阶段 | 玩家操作 / 代码 | 具体落点 |
|---|---|---|
| ① 观察环境 | 只读 | 读 `game.market` / `weather` / `policy` / 各公司 `last_income`、`price` |
| ② 基建·资源·人力调度 | **UI 操作段**（`end_turn` 前） | `game.build` / `hire` / `fire` / `borrow`；**新增**：`set_manpower_split`、`start_research`、`deploy_team`、`sign_contract` |
| ③ 设定电价 | **UI 操作段**（`end_turn` 前） | 直接改 `Company.res_price` / `ind_price`（界面滑杆） |
| ④ 结算经营 → 财报 | `end_turn` 内 | B 工程推进 → C 生产结算 → **R 研发结算（新）** → D 政策 → **S 合同/信誉（新）** → E 股利 → F 财务 |
| ⑤ 股市并购 | `end_turn` 内 + UI | G 股价刷新 → H 控股判定；UI 买卖股本身是即时操作 |
| ⑥ 事件/政策/城市扩张 | `end_turn` 内 | I 随机事件（**灾害写 `disaster_result`**）→ J 下回合（**城市扩张新增**） |

完整调用序（新系统插入点已标注为加粗）：

```
A  AI 行动            ai.ai_turn()            含 AI 研发决策
B  在建工程推进       advance_projects()      只吃【基建配额】
C  生产结算           settle_production()     写 outage_hours_by_city（唯一源）
R  研发结算 ★新增     settle_research()       扣钱 + 算概率 + roll
D  政策结算           apply_quota_penalty / check_antitrust
S  合同/信誉结算 ★新增 settle_contracts() / settle_trust()  读 outage_hours
E  股利               collect_dividends()
F  财务结算           settle_finance()        研发费、合同收入、应急维护费在此进利润表
G  股价刷新           update_all_prices()
H  控股判定           check_control()
I  随机事件           roll_event()            灾害写 disaster_result
J  进入下一回合       _advance_turn()         城市扩张在此跑
L  胜负判定           _check_end()
```

> **为什么 R 在 C 之后而不是 B 之后**：`settle_production()` 第 116 行会把 `co.last_income` 重置为新的
> `IncomeStatement()`。研发费用必须写进**重置之后**的当期利润表，否则会被清空。
> 结论：R、S 都必须在 C 之后、F 之前。

## 4. 术语表（全工程统一，禁止同义词）

| 术语 | 定义 | 代码字段 |
|---|---|---|
| 回合 | 1 季度 = 2190 小时 | `Game.turn` |
| 工程总池 | 公司可支配的工程队总数 | `Company.eng_teams` |
| 基建配额 | 本期允许在建工程占用的工程队数 | `Company.infra_quota` ★新 |
| 研发配额 | 本期允许在研项目占用的工程队数 | `Company.research_quota` ★新 |
| 累计时长 | 研发项目**当前**已累计的失败/投入回合数 | `ResearchProject.accumulated_rounds` ★新 |
| 最佳时长 | 该项目历史最高累计时长（撤项后保留） | `ResearchProject.best_accumulated_rounds` ★新 |
| 口碑 | **可见**的公众评价，驱动客户分流 | `Company.reputation`（现有） |
| 信誉 | **隐藏**的履约信用，驱动合同与 AI 合作 | `Company.trust` ★新 |
| 断电时长 | 本期客户侧实际停电的小时数 | `City.outage_hours` / `Company.outage_hours_by_city` ★新 |
| 灾难结果 | 一次灾害结算后的唯一结果对象 | `Game.disaster_result` ★新 |
| 研发修正 | 事件对研发的修正，单一数据源 | `Game.research_modifier` ★新 |

> **口碑 ≠ 信誉**。口碑是"客户现在喜不喜欢你"（事件、罚款、裁员立竿见影）；
> 信誉是"别人敢不敢把长期合同交给你"（由断电时长与违约缓慢积分）。
> 二者的耦合只有一处：**口碑的回归目标 = 45 + 0.30 × 信誉**（默认信誉 50 → 目标 60，与现有代码行为一致）。

## 5. 胜负与张力

胜利条件不变（沿用 `DESIGN.md` §4）：

- 🏆 **霸权结局**：全市场供电份额 ≥ 50% 且总市值第一
- 🌿 **绿色转型结局**：新能源占比 ≥ 55%、碳强度 ≤ 180g/kWh、碳税进入最高档
- 💀 **失败**：资不抵债破产 / 被 AI 持股 ≥ 51%

新增系统**不改变胜负条件**，只改变达成路径的摩擦：

| 摩擦 | 来源 | 玩家感受 |
|---|---|---|
| 研发烧钱不出成果 | 03：每回合刚性扣费 + 硬上限 | "我三个亿砸下去，核电还是只有 14%" |
| 省应急组 → 灾害断电 → 信誉崩 → 合同罚款 | 04 | "省了 300 万一季，赔了 5000 万" |
| 收购继承在建项目但养不起研发人力 | 03 §10 | "技术买来了，人还得自己养" |
| 高价值合同签不下来 | 04 §3：信誉 + 应急组双门槛 | "AI 数据中心就在那，我没资格签" |

## 6. UI 契约

主界面按**五个固定分区**布局（对齐 2026-05 的版式稿），地图永远占最大面积：

```
┌───────────────────────────────────────────────┬──────────────┐
│ 数据条：现金 负债 股价 市值 市占 监管（青边）   │ 时间块（蓝）  │
│                                               │ 回合/年季/结束 │
├────┬──────────────────────────────────────────┴──────────────┤
│页签│                                                          │
│政策│                                                          │
│股市│                    地  图（自动缩放铺满）                 │
│公司│                                     ┌──────────────────┐ │
│────│                                     │ 抽屉：选中的面板   │ │
│其它│                                     └──────────────────┘ │
├────┴────────────────────────────────────────────────────────┤
│ 建造条：煤 气 水 风 光 核 变 线 矿 + 取消（红边）              │
└──────────────────────────────────────────────────────────────┘
```

| 分区 | 内容 | 关键约束 |
|---|---|---|
| 数据条（上左） | 现金 / 负债 / 股价 / 市值 / 市占 / 监管阶段 | 只读；股价红涨绿跌（见 `chg_pct()`） |
| 时间块（上右） | 回合 + 年季 + 需求、**结束回合** | 结束回合只在右侧时间块里，别在别处复制 |
| 页签轨（左） | 政策 / 股市 / 公司，下方"其它"= 存档/读档/规则 | 再点一次收起抽屉；`Ctrl+1~3` |
| 地图（中） | 2D 格子地图 + 图例条 + 地块信息 | 格子边长按可用面积自动算（`_fit_map`），不写死 |
| 建造条（下） | 8 种建筑 + 取消 + 内联校验原因 | 按钮自动置灰并写明原因；`Esc` 退出建造 |
| 抽屉 | 政策·日志 / 股市·行情 / 公司（运营·财报） | 盖在地图右侧，**不挤压地图**；`Esc` 收起 |

**面板职责**（原来的"经营/财报"页合并进"公司"）：
- **政策**：政策台阶、大宗价格、天气、回合动态日志；
- **股市**：K 线、行情表、买卖/回购/增发、控股处置、对手情报；
- **公司**：`运营`（资金/定价/电厂/人力/分红）与 `财报`（利润表 + 净利走势）两段切换。

**后续新增系统的落位**（M1~M3 实现时）：研发 → 页签轨第 4 项；合同·应急 → 公司面板新增一段，
或在页签轨追加一项。两者都不改五个固定分区的结构。

**研发面板的一行显示范式**（照抄，别改）：

```
超临界燃煤 600MW   累计 5 回合（+12.5%）   当前成功率 34%   条件 2/3   1800万/回合  2 队
配套：✔ 在运燃煤  ✔ 自有煤矿  ✘ 电网≥600MW
```

**无进度条的三个理由**（写进代码注释，防止后来人加回来）：
1. 进度条暗示"必然完成"，而本作的核心情绪是"可能永远失败"；
2. 进度条会让玩家把研发当建造队列，从而低估现金流压力；
3. 显示"当前成功率"已经给了玩家全部决策信息，进度条是冗余。

## 8. 与现有实现的冲突与裁决

先摆冲突，再给裁决。**裁决即契约**，实现时照此执行。

| # | 冲突 | 裁决 |
|---|---|---|
| C1 | 研发文档说"小火电上限 50%"，又说"小型火电默认解锁无需研发" | **自相矛盾**。裁决：默认解锁的是 `coal`（现有 300MW 燃煤），"上限 50%"指的是**亚临界中型机组**这一将来型号。本期 8 个研发项目不含"小火电"，把 50% 上限给 `usc_coal`（超临界燃煤） |
| C2 | 研发费用"费用化进利润表"，但 `IncomeStatement` 没有该科目 | 新增 `research` 字段，计入 `operating_cost`；`rows()` 增加一行"研发费用" |
| C3 | 现有 6 种电源开局全部可建；研发文档要求默认只解锁 3 种 | 裁决：**现有 6 种全部保留为"基础型号"**（视为默认解锁），研发只解锁**新增的高阶型号**（03 附表 8 个）。这样既满足"默认解锁用配置标记"，又不破坏 V1.0 平衡 |
| C4 | 城市是 4 座定点单格、`base_mw` 无条件下增长 | 02 改为区块模型；`base_mw` 降级为**派生缓存**（`Σ 区块负荷`），`growth` 由扩张意愿派生，保持 `_advance_turn` 的调用签名不变 |
| C5 | 已有可见 `reputation`，文档又要"隐藏信誉" | **双变量**：`reputation`=口碑（可见、快变量）、`trust`=信誉（隐藏、慢变量）；口碑回归目标 `45 + 0.30 × trust` |
| C6 | 地图是手搓的，文档要生成管线 | 01 定义生成管线，但**输出契约 = 现有 `WorldMap` 的字段**（`tiles/cities` + `check_build` 语义），只增字段不删字段 |
| C7 | `eng_teams` 是一个整数池 | 拆为 `infra_quota + research_quota = eng_teams`，**回合开始锁定**；池子总量仍叫 `eng_teams`，`advance_projects` 改吃 `infra_quota` |
| C8 | 文档说"阶段 4 财报前"结算研发，但代码在 C 步重置利润表 | R/S 落在 **C 之后、F 之前**（见 §2 说明） |
| C9 | 储能在现有 `dispatch` 里没有充放模型；特高压超出 `grid` 的 180/120MW 接口模型 | 本期**简化**：储能按"CF 0.25 的调峰机组"结算；特高压变电站按"接口 +600MW，造价 ×4"结算。真正的充放/潮流留给 V2.x，写进 03/00 的风险表 |
| C10 | 合同要"承诺供电量"，现有是"按份额自动分流" | 合同不改分流算法。合同客户 = 该城负荷的一个**切片**，实际供电 = 该公司在该城的份额 × 切片负荷。签约不锁客户，只承诺"我保证供到 X MW" |
| C11 | 合同示例 `price_cap: 95`，但现网电价是 460~520 元/MWh，量纲不同会永远违约 | 合同电价一律改写成"**市场均价 × 系数**"（工业 0.95 / 绿电 1.12 / AI 数据中心 1.15），绝对值由 `game.market` 推出 |
| C12 | 现有 `_ev_storm` 既停机又直接 `reputation −4`，新灾害系统还会再扣一次信誉 | 删除事件内的直接扣口碑，只保留机组停机；口碑与信誉统一由 `disaster_result → 信誉` 结算，**禁止双罚** |

**未裁决、留待数值验证的两条**（实现时必须先跑 48 回合模拟）：

- 信誉侵蚀系数 0.5/小时 + 季度 2190 小时，意味着"任何 5% 以上缺供都会打满单回合上限"。
  契约里用 `EROSION_CAP = 15` 兜底，但是否降到 0.15 需要 `tools/sim.py` 实测。
- 研发 8 项全开 1.91 亿/回合，超过玩家中前期单季净利（±1 亿）。
  这是刻意的，但需要验证"只开 1~2 项能否在 20 回合内拿到第一个高阶型号"。

## 9. 避坑清单（12 条，按踩坑概率排序）

1. **不要给研发加进度条**。加了就等于承认"投入必然产出"。
2. **不要把研发做成"点了就等"**。每回合必须同时扣钱、占人力、暴露风险，三者缺一就退化成挂机。
3. **不要让 8 个项目同时可开**。受研发配额与现金双重约束，玩家必须做取舍。
4. **不要把 `global_max_rate` 写成 `1.0`**。高难度型号永远有失败概率，这是本模块的情绪核心。
5. **不要为断电做第二套统计**。信誉、合同、城市一致读 `outage_hours_by_city`。
6. **不要用硬编码判断解锁**。`default_unlocked` 数组 + `unlocked` 集合，新增型号不改代码。
7. **不要把研发费用资本化**。费用化才能形成"烧钱→利润跌→股价跌→被偷袭"的传导链。
8. **不要让 AI 研发对玩家透明**。玩家只能看到 AI 已建成的型号。
9. **不要撤项时清空累计时长**。`accumulated_rounds` 与 `best_accumulated_rounds` 分开存。
10. **不要把信誉显示成数字**。5 档文字 + 间接信号；调试模式才显示数值。
11. **不要让应急组变成纯正收益**。维护费必须刚性、必须上财报，否则玩家无脑堆。
12. **不要让合同变成白送钱**。每份合同都要有可失败的硬条件（供电量/断电时长/电价），否则就是无风险套利。

## 11. 跨文档不变量（验收总纲）

以下 8 条对所有子契约生效，任何一条被破坏都视为契约失效：

1. **数值单一源**：所有可调数字来自 `constants.py`（或它读入的 JSON），文档里出现的数字必须能在其中找到。
2. **单位统一**：万元 / MW / MWh / 元每 MWh / 吨 / 回合。
3. **状态机合法**：任何状态转移必须在 03 §4 的转移表里，禁止隐式跳转。
4. **数据单一源**：`outage_hours`、`research_modifier`、`disaster_result` 各只有一处写入点。
5. **财报闭合**：任何新增收支都必须出现在 `IncomeStatement.rows()`，否则玩家看不见。
6. **存档兼容**：所有新增 dataclass 字段必须有默认值（`pickle` 旧档能读）。
7. **无进度条**：UI 层不允许出现研发进度条/百分比进度。
8. **可回退**：删掉 03/04 的调用点，游戏必须仍能跑完整个回合（新系统是叠加层，不是主干）。

## 12. 待补的接口约定（跨系统）

1. `Company.infra_quota / research_quota` 由 UI 设置，`end_turn` 开头读取并冻结，回合内不可变。
2. `settle_research()` 必须在 `settle_production()` 之后调用（利润表重置问题，见 §2）。
3. `settle_contracts()` 必须在 `settle_research()` 之后、`settle_finance()` 之前。
4. 灾害事件必须写 `game.disaster_result`，不得直接扣信誉/直接改合同。
5. 城市扩张必须在 `_advance_turn()` 内、天气与需求重置之后执行（否则用到过期数据）。
6. AI 研发决策放进 `ai.ai_turn()` 的第 6 个子步骤，不新增独立遍历。
7. 所有新增 UI 只读 `Game` 的公开字段，不允许反向改引擎状态（除玩家显式操作 API）。
